# AI Gateway Platform — 智能路由决策层 技术文档（v1.0）

## 1. 项目定位

### 1.1 一句话

在已有 AI Gateway Platform（LLM API 网关与计费系统）之上，新增**多模型智能路由决策层**，把网关从"被动转发"升级为"主动决策"：请求不指定模型时，系统依据请求特征、租户预算、延迟 SLA、模型实时健康与质量，自动选择最优模型；指定模型时，仅在约束下放行或降级。

### 1.2 要解决的核心矛盾

不同 LLM 的定价与能力差距显著，同一请求走强模型和弱模型的成本可能相差一个数量级，而多数请求并不需要最强模型。已有网关只解决"接得住、算得清、扛得住"，路由是"客户端指定 + 故障降级"，不解决"该用哪个模型"的问题。本模块补上决策层。

### 1.3 与已有系统的关系（重要）

**不是两个项目，是一个系统的两次迭代。**

| 阶段 | 解决的问题 | 核心能力 |
|---|---|---|
| 第一版（已有） | 接得住、算得清、扛得住 | 统一入口、OpenAI 兼容、SSE、精确计费、原子配额、降级补偿、三级流控、ES 检索 |
| 第二版（本模块） | 选得对、省得下 | 请求特征提取、策略链路由决策、预算/SLA 约束、在线质量与延迟统计、路由可观测 |

**复用关系**：新模块复用现有 Redis（统计缓存）、RabbitMQ（统计旁路更新）、`t_invoke_log`（决策日志）、Sentinel（健康分）、`traceId`（全链路审计），不新增中间件、不新增 MQ 队列、不新增核心表。

| MySQL | 8.x | 本地 Windows MySQL（已有） | 作为服务运行 |

### 2.2 Redis 方案说明（本次变更）

- **选型**：使用社区编译的 Redis for Windows（`Redis-<版本>-Windows-x64-msys2.zip`），**不注册 Windows 服务**，不常驻后台。
- **使用方式**：解压到项目 `tools/redis/` 目录；需要时由启动脚本拉起 `redis-server.exe`，用完关闭进程即停止。满足"平时关闭、用时才开"的需求。
- **选型理由**：完全免费、无许可限制（对比 Memurai 开发版的 10 天重启与禁止生产条款）；解压即用、无安装依赖；与现有 Spring Boot RedisTemplate、Another Redis Desktop Manager 客户端协议兼容，业务代码无需改动。
- **兼容性**：现有网关使用的限流 Lua、ZSet 滑动窗口、配额缓存等均为 Redis 基础能力，跨版本稳定，无兼容风险。

### 2.3 环境约束与应对

- **全部中间件运行于 Windows 本机**，不依赖 Linux 虚拟机，满足"提交全部代码+配置即可复现"的课设要求。
- **MySQL 使用本地实例**，远程 MySQL 作为备选方案在 README 中说明。
- **模型使用本地 Ollama**，演示时用两个模型对比（强模型 + 便宜模型），成本差异由现有千 token 定价表模拟，不依赖付费 API。
- **Redis 客户端**用已有的 Another Redis Desktop Manager 查看数据，服务端为社区编译版 Redis。
- **中间件按需启停**：除 RabbitMQ 作为服务常驻外，Nacos、ES、Redis、Sentinel、Ollama 均可由脚本按需拉起，演示结束可停止，便于提交环境的整洁复现。

### 2.4 配置提交策略

- `application.yml` 使用占位符（如 `${MYSQL_HOST:localhost}`），凭据不硬编码。
- 本地开发配置放 `application-local.yml`，不提交。
- Sentinel 规则从 Nacos 导出为 JSON，放入 `configs/nacos/sentinel-rules/` 一并提交。
- 提交物包含中间件**配置说明与启动脚本**，不包含第三方二进制（Redis 解压包在 `tools/` 中提供下载说明，或按课程要求决定是否纳入提交）。

## 3. 系统架构

### 3.1 架构增量

在已有架构上，新增部分用【新增】标注：

```
客户端
  │
网关 gateway:10011（JWT + Redis 限流 + Sentinel）
  │
  ├─ /auth/**   → auth:8091
  ├─ /v1/**     → router:8092
  │                 ├─【新增】RoutingEngine（策略链 + 打分，内嵌）
  │                 ├─ 调用 Ollama 模型
  │                 └─ 发 MQ（chat.record.mysql / chat.record.es）
  ├─ /admin/**  → admin:8084
  │                 └─【新增】路由分析接口
  └─ /api/user/chat/** → es-sync:8085

billing:8093（消费 chat.record.mysql）
  ├─ 现有：计费、配额原子扣减、日汇总
  └─【新增】更新 Redis 中的模型延迟/质量统计

基础设施：Nacos / RabbitMQ / ES / Redis / Sentinel / Ollama / MySQL
```

### 3.2 请求流转（含智能路由）

```
请求进入 /v1/chat/completions
  → 解析 model 字段
      ├─ 指定 model：校验存在且启用 → 进入现有流程
      └─ 未指定：进入 RoutingEngine
            → 特征提取（长度/代码/问题数/租户等级）
            → 候选池过滤（启用 + 健康）
            → 预算过滤（剩余配额 ≥ 预估成本）
            → 复杂度匹配（simple→便宜池 / complex→强模型池）
            → 延迟过滤（预测延迟 < SLA）
            → 加权打分排序，选 top1
            → 记录决策到 t_invoke_log.routing_decision
  → 调用模型（失败走现有 fallback_code 降级）
  → 发 MQ 记账与统计
```

## 4. 核心业务逻辑

### 4.1 请求特征提取（规则版，不引入大模型）

| 特征 | 提取方式 | 用途 |
|---|---|---|
| 输入长度 | messages 总字符/token 估算 | 成本预估、复杂度 |
| 是否含代码 | 正则匹配代码块/关键字 | 复杂度加分 |
| 问题数量 | 问号/分句统计 | 复杂度加分 |
| 租户等级 | 用户表字段 | 可用模型池 |
| 会话轮次 | 历史消息数 | 上下文成本 |

**复杂度分级**：simple / balanced / complex，规则打分映射，后续可替换为小分类器。

### 4.2 路由策略链（可组合、可解释）

```
候选模型池 → 预算过滤 → 复杂度匹配 → 延迟过滤 → 加权打分 → top1
```

- **预算过滤**：预估成本 ≤ 租户剩余配额，否则剔除。
- **复杂度匹配**：simple 只进便宜池，complex 只进强模型池，balanced 全池。
- **延迟过滤**：请求头 `X-Latency-SLA` 存在时，剔除预测延迟超标的模型。
- **加权打分**：`score = w_q × 归一化质量分 − w_c × 归一化单价`，权重可配置。
- **决策可解释**：每个被剔除的候选记录原因，最终写入 `routing_decision` JSON。

### 4.3 在线统计（复用 MQ 旁路）

- `billing` 消费 `chat.record.mysql` 时，在现有逻辑末尾更新 Redis：
  - 模型近 N 次延迟（ZSet 或 List，滑动窗口）
  - 模型质量代理分（规则：非空、未拒答、结构合理）
  - 模型错误计数（配合 Sentinel 健康分）
- 统计更新**不阻塞主链路**，决策时读 Redis 内存值。

### 4.4 降级与路由的关系

- **路由是事前选择**，降级是**故障兜底**，两者互补。
- 降级成功后，现有"按实际应答模型计价"逻辑不变，`routing_decision` 中记录降级事件。

### 4.5 可观测

- `t_invoke_log` 新增 `routing_decision` 字段（JSON）：候选模型、过滤原因、最终选择、预估成本、实际成本、实际延迟。
- 管理端新增"路由分析"接口与页面：全强模型基线 vs 智能路由的成本/延迟对比。

## 5. 数据模型

### 5.1 表结构变更（最小化）

| 表 | 变更 | 说明 |
|---|---|---|
| `t_invoke_log` | 新增 `routing_decision` JSON/TEXT 字段 | 存决策详情，可空（指定模型时为 null） |
| `t_model_quality_stat`（可选） | 若需持久化统计再建；否则仅存 Redis | 建议先只存 Redis，降低改动 |

### 5.2 Redis 键设计

| 键 | 类型 | 说明 |
|---|---|---|
| `route:latency:{modelCode}` | ZSet | 近 N 次耗时，score=时间戳 |
| `route:quality:{modelCode}` | Hash | 质量分、样本数、错误数 |
| `route:health:{modelCode}` | String | 健康分（由 Sentinel 状态与错误率合成） |

## 6. 接口契约

### 6.1 对话接口变更（向后兼容）

`POST /v1/chat/completions`

- `model` 字段改为**可选**：不传则智能路由；传则按现有逻辑。
- 新增可选请求头：
  - `X-Cost-Budget`：本次请求成本上限
  - `X-Latency-SLA`：延迟目标（毫秒）
- 响应新增字段（不破坏 OpenAI 兼容）：
  - `routing_decision`：决策摘要（选中模型、原因、预估成本）

### 6.2 管理端新增

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/routing/analysis` | 路由分析：成本对比、模型分布、决策原因统计 |
| GET | `/admin/routing/decisions` | 决策日志查询（按 traceId/用户/时间） |

## 8. 演示与答辩要点

### 8.1 演示脚本

1. 发简单请求（不指定 model）→ 路由选便宜模型 → 展示决策日志。
2. 发复杂请求（含代码/长文本）→ 路由选强模型 → 展示决策日志。
3. 带 `X-Cost-Budget` 的低预算请求 → 路由降级到便宜模型。
4. 打开路由分析看板 → 展示"全强模型基线 vs 智能路由"成本对比。

### 8.2 预期追问与回答

| 问题 | 回答要点 |
|---|---|
| 已有 fallback 为何还要路由 | 降级是故障兜底，路由是事前选择；降级不省钱，路由才是成本杠杆 |
| 决策是否拖慢主链路 | 纯内存计算 <5ms；统计更新走 MQ 旁路 |
| 质量分是否准确 | 代理指标（规则打分），精度换低开销，可后续接 LLM-judge 校准 |
| 与商业多模型网关区别 | 策略链可解释、决策落库可审计、与计费配额深度耦合 |
| Redis 为何不注册为服务 | 课设环境按需启停，避免常驻；社区编译版免费无许可限制 |

### 8.3 简历描述模板

> 在自研 LLM API 网关（Spring Cloud 微服务，含认证、计费、配额、三级流控、死信补偿、ES 检索）之上，新增智能路由决策层：请求不指定模型时，依据请求复杂度、租户预算余量、延迟 SLA、模型实时健康与近期 P99，执行"预算过滤→复杂度匹配→延迟过滤→加权打分"策略链自动选型；模型统计复用 RabbitMQ 异步记账链路旁路更新，不阻塞主链路；管理端提供全默认 vs 智能路由的成本/延迟对比。压测对比全走强模型基线，成本降低约 XX%，P99 满足 SLA，规则打分质量保持基线 XX% 以上。

## 9. 风险与边界

| 风险 | 应对 |
|---|---|
| 路由决策影响现有主链路稳定性 | 决策为旁路增强，指定 model 时行为不变；灰度开关控制 |
| 统计不准导致选型偏差 | 规则打分 + 质量下限约束；低质量模型短期拉黑 |
| Windows 中间件启动顺序敏感 | `start-all-windows.bat` 内置等待；README 写明就绪判断 |
| 远程 MySQL 不可达 | 本地 MySQL 为主，README 提供两种配置 |
| Redis 按需启动导致服务未就绪 | 启动脚本内做端口探测（如 `ping` 命令）后再启动后端；README 注明 |
